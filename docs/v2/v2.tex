\section{Resolución de Ejercicios Prácticos de Gestión de Flujo Ágil}

A continuación, se presentan las respuestas fundamentadas a los dos ejercicios prácticos desarrollados en clase, aplicadas de manera directa y pedagógica a la realidad de nuestro proyecto \textbf{SIGC-CUSCO}.

\subsection{Ejercicio 1: Una Revisión Saturada (Gestión de Flujo y Cuellos de Botella)}
\textbf{Escenario Planteado:} \textit{El límite de la columna Revisión (Review) es 1 y ya existe un ítem esperando en cola.}

\begin{enumerate}
    \item \textbf{¿Conviene iniciar la tarea de recordatorios? Justificación:}
    \begin{itemize}
        \item \textbf{Respuesta: NO conviene iniciarla.}
        \item \textbf{Fundamento Ágil:} En el marco Kanban rige el principio fundamental: \textit{“Stop starting, start finishing”} (Dejar de empezar cosas nuevas y enfocarse en terminar lo que está en curso). Si la columna de \textit{Revisión} tiene un límite WIP (\textit{Work In Progress}) de 1 y ya se encuentra saturada, abrir una nueva tarjeta de desarrollo (como "Módulo de Recordatorios") generará acumulación de inventario intermedio no validado, aumentará el tiempo de ciclo (\textit{Lead Time}) del equipo y saturará aún más el cuello de botella.
    \end{itemize}

    \item \textbf{Acuerdo de Colaboración: ¿Cómo ayudaremos a terminar la revisión?}
    \begin{itemize}
        \item Se aplica la técnica de \textbf{Swarming / Mob Review}: El desarrollador que terminó su tarjeta se pone a disposición del revisor en lugar de iniciar código nuevo.
        \item El compañero apoya realizando pruebas cruzadas (\textit{peer testing}) en local, verificando que los criterios de aceptación se cumplan y ayudando a resolver inmediatamente las observaciones de código detectadas. De esta manera, el ítem en revisión se promueve rápidamente a \textbf{Done} y el flujo se reactiva de forma saludable.
    \end{itemize}

    \item \textbf{Protocolo de Actuación ante una Tarjeta Bloqueada:}
    \begin{itemize}
        \item \textbf{Señalización Visual Inmediata:} Se le asigna una etiqueta roja destacada con el estado \texttt{[BLOQUEADA]} en el tablero.
        \item \textbf{Registro de Causa Raíz:} Se documenta en la tarjeta la causa exacta (ej. \textit{“Falta acceso a la API del validador de DNI”} o \textit{“Falta confirmación de firmas de la municipalidad”}).
        \item \textbf{Regla de Escalamiento:} Una tarjeta bloqueada no cuenta para saturar el desarrollo de quien la ejecutaba, pero adquiere máxima prioridad para el facilitador del equipo, quien debe gestionar el impedimento en un plazo no mayor a 24 horas.
    \end{itemize}
\end{enumerate}

\begin{tcolorbox}[colback=blue!4!white, colframe=blue!70!black, title=\textbf{Políticas de WIP y Bloqueo Adoptadas en SIGC-CUSCO}, arc=1.5mm]
\begin{itemize}\setlength\itemsep{0.1em}
    \item \textbf{Límites WIP Oficiales:} \textit{To Do} = 5 máx. \textbar{} \textit{In Progress} = 2 máx. \textbar{} \textit{Review / QA} = 1 estricto \textbar{} \textit{Done} = Ilimitado.
    \item \textbf{Política de Bloqueo:} Si un ítem se bloquea, el equipo dedica la primera mitad de la reunión de coordinación (\textit{Daily}) a destrabarlo antes de iniciar cualquier otra discusión.
\end{itemize}
\end{tcolorbox}

\section{Diseño de Base de Datos y Esquema Relacional}

Para implementar el sistema con máxima integridad referencial y soporte transaccional ACID, se emplea el gestor relacional \textbf{PostgreSQL}.

\subsection{Explicación Didáctica de las Conexiones Relacionales}
Para explicar a nuestros compañeros cómo interactúan las tablas en la base de datos, se establecen tres patrones relacionales:

\begin{enumerate}
    \item \textbf{Relación Uno a Muchos (1 a N):}
    \begin{itemize}
        \item \textbf{Ejemplo:} \texttt{Institución} (1) $\longrightarrow$ \texttt{Capacitación} (N).
        \item \textbf{Explicación simple:} Una sola municipalidad puede dictar muchos cursos durante el año, pero cada curso pertenece exclusivamente a una sola institución responsable. La llave primaria \texttt{id\_institucion} viaja a la tabla \texttt{capacitacion} como llave foránea (\textit{Foreign Key}).
    \end{itemize}

    \item \textbf{Relación Muchos a Muchos (N a M) resuelta por Tabla Intermedia:}
    \begin{itemize}
        \item \textbf{Ejemplo:} \texttt{Participante} (N) $\longleftrightarrow$ \texttt{Capacitación} (M).
        \item \textbf{Explicación simple:} Un participante puede inscribirse a varios cursos a lo largo del tiempo, y a su vez un curso tiene decenas de participantes. En bases de datos relacionales no se conectan directamente; se crea la tabla intermedia \textbf{\texttt{inscripcion}}, que guarda la combinación de ambos con su fecha y estado.
    \end{itemize}

    \item \textbf{Relación Uno a Uno (1 a 1 Condicional):}
    \begin{itemize}
        \item \textbf{Ejemplo:} \texttt{Inscripción} (1) $\longrightarrow$ \texttt{Certificado} (0..1).
        \item \textbf{Explicación simple:} Cada registro de inscripción que cumpla con asistencia y nota aprobatoria genera exactamente un único certificado oficial. No pueden existir dos certificados distintos para la misma inscripción.
    \end{itemize}
\end{enumerate}

\subsection{Esquema Físico de Base de Datos (Script DDL en PostgreSQL)}
A continuación se detalla el código SQL listo para ser ejecutado:

\begin{tcolorbox}[breakable, colback=CodeBg, colframe=black!40, title=\textbf{Script DDL PostgreSQL -- SIGC-CUSCO}, arc=1mm]
\small
\begin{verbatim}
-- 1. Tabla de Instituciones (Multitenancy)
CREATE TABLE instituciones (
    id_institucion SERIAL PRIMARY KEY,
    ruc VARCHAR(11) UNIQUE NOT NULL,
    razon_social VARCHAR(150) NOT NULL,
    tipo VARCHAR(20) CHECK (tipo IN ('Publica', 'Privada')),
    logo_url TEXT,
    activo BOOLEAN DEFAULT TRUE
);

-- 2. Tabla de Usuarios (RBAC)
CREATE TABLE usuarios (
    id_usuario SERIAL PRIMARY KEY,
    dni VARCHAR(8) UNIQUE NOT NULL,
    nombres VARCHAR(80) NOT NULL,
    apellidos VARCHAR(80) NOT NULL,
    correo VARCHAR(100) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    rol VARCHAR(20) CHECK (rol IN ('Admin', 'Coordinador', 'Docente', 'Alumno'))
);

-- 3. Tabla de Capacitaciones
CREATE TABLE capacitaciones (
    id_capacitacion SERIAL PRIMARY KEY,
    id_institucion INT REFERENCES instituciones(id_institucion) ON DELETE CASCADE,
    id_docente INT REFERENCES usuarios(id_usuario),
    titulo VARCHAR(150) NOT NULL,
    horas_academicas INT NOT NULL CHECK (horas_academicas > 0),
    vacantes_max INT NOT NULL CHECK (vacantes_max > 0),
    fecha_inicio DATE NOT NULL,
    estado VARCHAR(20) DEFAULT 'Planificada'
);

-- 4. Tabla Intermedia: Inscripciones
CREATE TABLE inscripciones (
    id_inscripcion SERIAL PRIMARY KEY,
    id_capacitacion INT REFERENCES capacitaciones(id_capacitacion),
    id_participante INT REFERENCES usuarios(id_usuario),
    fecha_registro TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    estado VARCHAR(20) DEFAULT 'Confirmada',
    CONSTRAINT uq_participante_curso UNIQUE (id_capacitacion, id_participante)
);

-- 5. Tabla de Asistencias (Con soporte QR y Offline)
CREATE TABLE asistencias (
    id_asistencia SERIAL PRIMARY KEY,
    id_inscripcion INT REFERENCES inscripciones(id_inscripcion) ON DELETE CASCADE,
    numero_sesion INT NOT NULL,
    fecha_hora TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    estado VARCHAR(15) CHECK (estado IN ('Presente', 'Tardanza', 'Falta')),
    metodo VARCHAR(15) DEFAULT 'QR_Digital'
);

-- 6. Tabla de Certificados Criptográficos
CREATE TABLE certificados (
    id_certificado SERIAL PRIMARY KEY,
    id_inscripcion INT UNIQUE REFERENCES inscripciones(id_inscripcion),
    codigo_unico VARCHAR(32) UNIQUE NOT NULL,
    hash_sha256 CHAR(64) NOT NULL,
    fecha_emision TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    url_pdf TEXT NOT NULL
);

\section{Herramientas para Diagramado Rápido y Colaborativo}

Para que cualquier integrante del equipo pueda elaborar y editar los diagramas de manera simple, se recomiendan las siguientes herramientas:

\begin{enumerate}
    \item \textbf{dbdiagram.io (Bases de Datos Relacionales):}
    \begin{itemize}
        \item \textbf{¿Por qué usarla?} Es la herramienta más rápida del mercado para crear modelos relacionales. Se escribe en lenguaje simple DBML (\textit{Database Markup Language}) y dibuja las tablas y las líneas de conexión automáticamente.
        \item \textbf{Sintaxis de ejemplo para conectar tablas:}
        \begin{verbatim}
        Ref: capacitaciones.id_institucion > instituciones.id_institucion
        Ref: inscripciones.id_capacitacion > capacitaciones.id_capacitacion
        \end{verbatim}
    \end{itemize}

    \item \textbf{Mermaid.js (Diagramas UML directo en GitHub y Markdown):}
    \begin{itemize}
        \item Permite crear diagramas de secuencia, casos de uso y entidad-relación sin instalar ningún software, renderizándose automáticamente en los archivos \texttt{README.md} de GitHub.
    \end{itemize}

    \item \textbf{Draw.io / diagrams.net (Modelado Visual Libre):}
    \begin{itemize}
        \item Herramienta gráfica gratuita conectada a Google Drive o VS Code para bocetar flujos y casos de uso en minutos.
    \end{itemize}
\end{enumerate}

\section{Plan de Evolución Incremental e Iterativo por Sprints}

Para cumplir con la premisa de evolución continua en cada clase, el desarrollo de \textbf{SIGC-CUSCO} se estructura en incrementos progresivos:

\begin{itemize}

    \item \textbf{Incremento 3 (Sprint Core Transaccional):} Implementación de portal de inscripción con validación de DNI y módulo de asistencia QR.
    \item \textbf{Incremento 4 (Sprint Certificación y Seguridad):} Renderizado de certificados PDF con código QR y validador público con hash SHA-256.
    \item \textbf{Incremento 5 (Sprint Analítica):} Dashboard institucional para municipalidades y empresas turísticas de Cusco.
\end{itemize}
